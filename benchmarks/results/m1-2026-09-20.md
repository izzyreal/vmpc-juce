# Initial M1 sanity check — 20 September 2026

Removing the optimization showed no meaningful CPU regression on this machine.
RAM was essentially unchanged in most cases; one noisy comparison was
inconclusive in the full sweep and passed a targeted repeat. This supports
the removal locally, but the older Windows machine still needs its own run.

The exact application revisions were `eeb8d07c7d5e2166fc2d2a1dd2d3febf491dd010`
(before) and `a45d440806f43b9702947ca22cc648aa23cfa5eb` (after). Both used
the same locked dependencies, including MPC
`99bfb9b65c2399edfdce5731036c6bf57f3ed176`. Hardware was an Apple M1 with
8 logical CPUs and 8 GiB RAM, running macOS 26.6.2; builds were native arm64,
AppleClang 21, Release (`-O3 -DNDEBUG`).

The full sweep used 48 kHz, six alternating before/after pairs per case,
36 sustained 32-voice cases and three idle controls. Each loaded case used
32 separate looping samples with filtering and resampling. Each timed trial
ran for at least two seconds and 2,000 callbacks after warmup.

| --- | ---: | ---: | ---: |
| 64 | −3.18% | −4.23% to −1.05% | −0.044 MiB |
| 256 | −0.92% | −1.63% to −0.45% | −0.061 MiB |

All 39 thread-CPU and mean-callback comparisons passed the default thresholds.
The table summarizes per-case changes, not a pooled confidence interval.

## Memory uncertainty and repeat

The full sweep's overall verdict was **INCONCLUSIVE**, solely because resident
memory for `48000/64 all mono32 drum` averaged 68.59 MiB before and 76.04 MiB
after. One before worker reported 31.38 MiB after timing; the other five were
around 76 MiB. This is consistent with OS reclamation/accounting noise, though
the measurements alone cannot prove its cause.

A fresh six-pair repeat of that exact case reported **ACCEPTABLE**:
76.07 → 76.03 MiB, with mean callback time 87.95 → 84.09 µs (−4.39%).
The original inconclusive result is retained; this repeat applies only to
that case. macOS resident memory is not a precise measure of owned allocations.
The Windows runner additionally compares private committed memory.

## Headroom and correctness

The worst after-version p99 callback used 22.31% of the deadline at 64 frames,
6.75% at 256, and 6.29% at 1024. Nevertheless, isolated wall-time overruns
occurred: 151 before and 145 after across the full sweep, and three each in
the targeted repeat. The automated headroom verdict therefore asks for review.
These offline observations include scheduling effects; they are not measured
audio-device dropouts or a guarantee of real-time reliability.

All stable-routing audio hashes matched across revisions. Voice checks held
at 32 for every loaded case. Separate allocation passes detected zero
callback-thread C++ allocations in both versions. The routing-tail check
observed zero individual-output tail energy before and positive energy after,
as expected from the fix.

## Reproduction and evidence

See the [benchmark instructions](../audio/README.md). The manual
`audio-benchmark` CI pipeline produces `audio-benchmark-windows7-x86.zip`;
extract it on the old PC and run `run-benchmark.cmd`. The Windows build and
actual Windows 7 startup remain to be validated in CI/on that PC.

[Recorded measurements and manifests](m1-2026-09-20.json) retain the per-trial
timings, memory, audio hashes, allocation checks, thresholds and comparisons
for both runs. Complete local worker requests/results/logs are under
`build/audio-benchmark/local-results/{full,repeat}` (ignored build artifacts).
The full sweep used the same worker source as the final package; subsequent
runner updates added case selection, before/after overrun reporting, and an
allocator self-test. Both build manifests are retained in the evidence.

Final-package validation passed all 13 smoke cases, reporting/allocator
self-tests, five builder tests, and CI configuration validation. The ZIP was
extracted and run from an independent folder with spaces in its name.
